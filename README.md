# Ship Sync

Marketplace connecting air and ocean shippers with customers shipping to West Africa (Ghana, Nigeria, Liberia, Togo, Côte d'Ivoire, Sierra Leone, Senegal).

**Stack:** Vite + React 19 + TypeScript + Tailwind CSS v4 + Motion on the front end; Express + Postgres (`pg`) on the back end with session auth (httpOnly cookie, bcrypt passwords). Without a `DATABASE_URL` the server falls back to an embedded Postgres (PGlite) in `./data/pglite`, so it runs anywhere with zero setup.

```bash
npm install
npm run dev      # API + Vite dev server on http://localhost:5000
npm run build    # front end → dist/
npm start        # production: Express serves dist/ + /api
```

Copy `.env.example` to `.env` (or set Replit secrets). On Replit, add a PostgreSQL database and `DATABASE_URL` is injected automatically.

**Live tracking.** Ocean shipments with an MMSI are tracked via [AISStream](https://aisstream.io) (set `AISSTREAM_API_KEY`); air shipments with an ICAO callsign via [adsb.lol](https://api.adsb.lol) (no key). Shippers enter these from their dashboard. Without a signal the tracking page shows an estimated position along the great-circle route from departure and ETA. `GET /api/track/:ref/position` (now includes `detail` — the carrier's AIS/ADS-B card: flag, type, reported destination, ETA, or the flight's scheduled route) and `GET /api/live/region` (vessels + flights near the West African coast, and per-port congestion counts) are public and clearly labelled as delayed, approximate and not for navigation. Coverage note: AISStream relies on community shore receivers, which are dense on the Atlantic approach (Canaries, Morocco, Portugal) but currently absent on the Gulf of Guinea coast — so the regional feed subscribes to the coast box plus the Atlantic approach, Europe and the US coasts (origin regions), port congestion counts read 0 until a coastal receiver comes online, and watched vessels are seen while within any coverage (last fix persisted).

**Demo accounts** (seeded on first run, password `shipsync`): customer `demo@shipsync.demo`, shippers `ops@atlanticbridge.demo` and `ops@goldcoast.demo`, admin `admin@shipsync.demo` (verifies shippers and sets plans at `/#/admin`; `ADMIN_EMAILS=a@x.com,b@y.com` grants admin to real accounts on boot). Shippers edit their own listing from the dashboard (`PATCH /api/shippers/me`) and manage clients end to end at `/#/dashboard/clients` — contacts and West-African consignees, direct bookings (no quote needed, public tracking ref), invoices with payments and a printable view, and a per-client activity timeline with reminders (`server/clients.ts`; marketplace customers become clients automatically when they book); signed-in shippers can also assign a ship or flight to a shipment straight from the Live map. The shipper **Overview** (`/#/dashboard/shipper`, `src/components/ShipperOverview.tsx`, data from `GET /api/shipper/overview` in `server/insights.ts`) opens with a needs-attention strip (late or stale shipments, overdue invoices, waiting leads, follow-ups, runs today), KPI tiles with 30-day trends and sparklines (invoiced, quotes, win rate, active shipments), a 12-week quotes-vs-wins chart with hover, pipeline, lane mix, shipments by stage, today's operations (runs, fleet, drivers, follow-ups), quick actions and a recent-activity feed; the Gold Coast demo is seeded with ten weeks of history (`seedHistoryDemo`) so the trends have something to show. **Leads & quotes** (`/#/dashboard/leads`, `src/pages/Leads.tsx`) is the shipper's quote desk: stat cards for needs-a-reply (flagging leads waiting over a day), quoted, won (with booked value), lost and win rate that double as filters, Open/Won/Lost/All chips, search, mode/destination/sort synced to the URL, and a paginated table of requests on the shipper's lanes with route, cargo, customer, ready date, status and competition (other shippers' prices stay hidden — only the count shows); rows expand to the full request, contact details and either the quote form (price, transit, notes, auto-built inclusions) or the quote already sent with its outcome, and won leads link to the shipment they became. Three open demo leads are seeded (`seedOpenLeads`). **Shipments** (`/#/dashboard/shipments`, `src/pages/Shipments.tsx`) is a full board: stage cards (awaiting pickup, in transit, at destination, past ETA, no live tracking) that double as filters, search, mode/destination/sort controls synced to the URL, a paginated table with a progress strip per row, expandable rows with the tracking map, timeline, vessel/flight tracking form and links, one-click next step, CSV export and a New shipment flow that opens the booking form on the chosen client. **Containers** (`/#/dashboard/containers`, `src/pages/Containers.tsx` + `ContainerDetail.tsx`, API in `server/containers.ts`) is the consolidation workflow: book a container with the shipping line (size, line, booking ref, container number, seal, ports, cut-off/ETD/ETA, vessel + MMSI + voyage), load the ocean orders you have won into it from a candidate picker (same-lane orders first, other-lane warning, estimated fill bar from cargo type), then move it forward — Booked → Loading → Gated in → Sailed → Arrived → Customs → Devanned → Closed. Every stage change cascades to the loaded orders (Picked up / At origin port / In transit / Arrived / Customs), writes a customer-visible tracking event and, on sailing, copies the vessel and MMSI to each order so all of them are tracked live; vessel edits after sailing flow through as well. Orders can be removed until the container sails, stages only move forward, and drivers can't see containers. The Shipments board shows the container each order rides in. **Piece labels** (`/#/dashboard/labels?shipments=…`, `src/pages/Labels.tsx`, API in `server/labels.ts`): every shipment is split into pieces (`pieces` table — one per barrel, box or pallet; the count defaults to the quote quantity or the number at the front of the description and can be edited on the print page) and each piece gets a 4×6 in sticker with a QR code that opens the piece's tracking page, the reference in large type, destination port, receiver (consignee) and sender with phone numbers, contents, the container / seal / CN box (filled once the order is loaded, otherwise a dashed box to fill in by hand), and a Code 128 barcode for 1D scanners. Print from the Shipments board (per row, or every active shipment on the page) or from a container page (every loaded order); pick thermal 4×6 one-per-label or a Letter/A4 sheet four-up; printing stamps `printed_at`. **Scanner** (`/#/dashboard/scan`, `src/pages/Scan.tsx`, API in `server/scans.ts`; in the sidebar for every staff role and as *Scan to load* on a container page and *Scan a delivery* on the driver's My runs): the phone camera reads the sticker (BarcodeDetector where the browser has it, jsQR otherwise; a typed or USB-scanner code works too). Each scan means one thing — **loading** puts the piece in the chosen container and, on the first piece, joins the order to it and moves it to Picked up; **devanning** marks the piece received at the destination warehouse; **delivery** asks for who received it and an optional proof-of-delivery photo, and when the last piece is scanned the order becomes Delivered and its stop on the driver's delivery run is ticked off; **check** just records a sighting. Every scan writes a `scans` row (who, where, GPS if allowed, photo) and a customer-visible event ("Piece 2 of 4 loaded into container CN-2026-002 … (2 of 4)"), duplicates are recorded but change nothing (with a warning), and the customer's tracking page shows a pieces strip — one box per sticker with its state, and the piece they scanned highlighted via `?p=`. Container pages show pieces in/out per order. **Carrier tracking** (`server/carriers.ts`) connects a container's booking to the shipping line: `POST /api/containers/:id/tracking` subscribes it, a poller (`CARRIER_SYNC_MINUTES`, default 15) pulls the line's track & trace and fills in the container number, seal, vessel, IMO, voyage, ETD/ETA as they are assigned, resolves the vessel to an MMSI from the live AIS feed (so every loaded order is tracked on the map), and moves the container through Gated in → Sailed → Arrived from the line's own milestones — cascading to the orders exactly like a manual update, with each carrier event tagged "via carrier" on the timeline. Providers are pluggable through `CARRIER_TRACKING_PROVIDER` (unset = `terminal49` when `TERMINAL49_API_KEY` is present, else `mock`): `terminal49` ([Terminal49](https://terminal49.com) aggregator — one key covers every major line; on connect we open a tracking request by container number or booking number with the line's SCAC (auto-detect when the line isn't recognised), wait for the manifest, then read the shipment, its containers and transport events; vessels come back with an MMSI, the line's ETD/ETA override manual dates, and ids are kept in `containers.tracking_state` so each booking is only ever requested once), `mock` (a built-in simulator that assigns a number at once and then gates in, sails and arrives on a `MOCK_CARRIER_STEP_MINUTES` schedule, so the demo works without an account), `dcsa` (any line that publishes the DCSA Track & Trace v2 API — Maersk, MSC, CMA CGM, Hapag-Lloyd, ONE…: set `CARRIER_API_URL`, `CARRIER_API_KEY`, `CARRIER_API_KEY_HEADER`, `CARRIER_LABEL`), or `off`. Aggregators such as Vizion or Terminal49 slot in as one more adapter behind the same interface. Manual stage updates keep working on a connected container and never go backwards. Gold Coast is seeded with one sailed and one loading container plus three won orders waiting to be consolidated.  **Driver app niceties**: delivery scans capture the **receiver's signature** on the phone (finger on a canvas, saved as a small PNG) alongside the photo — it shows on the public tracking page and on the proof-of-delivery document; scans made with **no signal** are saved on the phone and sent automatically when the connection is back (with the original scan time), with a banner showing what is waiting and a *Sync now* button; every pending stop on a run has **Navigate** (Google Maps directions to the pin or address), **Call** and **WhatsApp** (pre-filled "I'm on my way" message) buttons; photos are already shrunk on the phone before upload. **White-label** (`server/brand.ts`; branded page `/#/t/<slug>`, editor `/#/dashboard/brand`): every shipper gets their own page with their logo, accent colour, headline, intro and contact buttons (call, WhatsApp, email), a tracking box, their published rates, verified reviews, and a quote form whose leads go **only to them** — never to competitors — and are priced instantly from their rate cards; guests create an account in the same step. Owners and dispatchers edit it (live preview), choose the address, toggle the rate list and the "Powered by Ship Sync" footer, and can connect their own domain: a CNAME at Ship Sync sends visitors on that host straight to the page. Booking, payment, tracking and documents all run on Ship Sync underneath. **Reviews & disputes** (`server/reviews.ts`; `ReviewCard` + `DisputeCard` on every shipment, shipper page `/#/dashboard/reviews`, real reviews on the public profile, admin mediation panel): only the customer of a delivered shipment can review — 1–5 stars, quick tags (on time, careful handling, hidden charges…) and text, shown on the shipper's profile as a verified review with the lane; the shipper replies once, publicly, and admins can hide abuse. The listing's rating blends real reviews with its seeded baseline so one review doesn't swing a new shipper to 1.0 or 5.0. Either side can open a **dispute** on a shipment that is in transit or later (damaged, missing, late, overcharged, not delivered, other, with an amount claimed); opening one puts the escrow payment **on hold** — no automatic or manual release while it is open — and notifies Ship Sync and the other side. Messages go back and forth in a thread (Ship Sync can post as mediator), the opener can withdraw, and an admin resolves with a full refund, a partial refund (the rest is released to the shipper), a release, or no action — each with a note both sides receive. Notification kinds `review` and `dispute`. **Analytics & lane intelligence** (`server/lanes.ts`; public explorer `/#/lanes`, shipper page `/#/dashboard/lanes`): the whole marketplace's quotes, anonymised, turned into benchmarks per lane (origin city → country, cargo type) — price p25 / median / p75 and range, quoted and actual transit, demand per week with trend, and win rate below vs above the median — plus the busiest lanes on the platform. Customers use it to sanity-check a quote; shippers see every lane they quoted in the last six months against the market (win rate, median price, % vs market, reply time), get plain-English pricing tips (above the market and losing, below the market and winning, slow replies), and a list of busy lanes outside their profile they could add. **Warehouse & yard** (`server/warehouse.ts`; `/#/dashboard/warehouse`): each shipper sets up its sites — an origin warehouse where customers drop off and a destination yard where goods wait for collection — with zones and bins (A-01 … A-12), free days and a storage rate per piece-day (and per vehicle-day). Staff **receive** pieces into a bin by sticker code or a whole shipment at once (stickers are created if they were never printed; receiving at the origin moves a booked shipment to *Picked up*), **move** them between bins and **release** them when they leave; the bin grid shows occupancy, the stock list shows days on hand and what is accruing, and recent movements are logged. Loading scans take pieces out of the origin yard and devanning scans put them into the destination yard automatically. Storage beyond the free days is priced per piece-day and dropped onto a draft invoice for the client with one click (the storage line is added to an existing draft if there is one). Gold Coast is seeded with a Houston warehouse (24 bins) and a Tema yard (8 bins) and a few shipments on hand, one past its free days. **Carrier booking** (`server/booking.ts`; shipper page `/#/dashboard/sailings`, public schedule `/#/sailings`, *Book space on a sailing* on an unbooked container): a rolling nine-week schedule of sailings per lane — Maersk, MSC, CMA CGM and Hapag-Lloyd container services and Grimaldi / Sallaum RoRo car carriers from Houston, Newark and Baltimore to Tema and Lagos — with vessel, voyage, ETD/ETA, document cut-off, rates per slot (20 ft / 40 ft / 40 HC, RoRo car / SUV / truck) and space left. The office books slots against a sailing for an existing container, a new container (created on the spot) or a RoRo vehicle shipment; the confirmation comes back with a booking reference and the vessel, voyage and dates are written onto the container / shipment so consolidation, labels and carrier tracking pick them up (the customer is told their vehicle's sailing). Bookings can be cancelled until the container gates in, which releases the slot. The built-in schedule provider (`SCHEDULE_PROVIDER=builtin`) rolls the schedule forward every 12 hours and confirms instantly; a real INTTRA / line API slots in behind `requestBooking()`. Admins add or edit sailings by hand (`POST /api/admin/sailings`). **Customs-broker marketplace** (`server/brokers.ts`; public directory `/#/brokers`, `CustomsCard` on every Ghana / Nigeria shipment, broker portal `/#/broker/<token>`, admin section): licensed clearing agents at Tema, Takoradi, Lagos (Apapa / Tin Can) and Onne are listed with licence details, specialties, response time and a flat clearance fee per cargo type. The customer or the shipper books one on a shipment; the broker gets an email with a private job link and works it without an account — accept (or decline), documents lodged, **assessed by customs** (the duty figure and ICUMS/NCS reference go straight onto the shipment's Duty card as the official assessment), duty paid, released from port, cleared & handed over — each step on the tracking timeline and notified to both sides. The office can move the job on for the broker, copy the broker link to WhatsApp, or cancel; a declined or cancelled job frees the slot for another broker. Admins list, edit and verify brokers. Six fictional brokers are seeded. Notification kind `customs`. **Online invoices & collections** (`server/collections.ts`; public pay page `/#/pay/<token>`, office page `/#/dashboard/collections`, customer tab *Invoices*): every invoice carries a pay link that shows the invoice and takes a card through the same Stripe / escrow rails — no sign-in needed, so clients added by hand can pay too. Paying marks the invoice paid, records the payment, emails a receipt and (when the invoice is for a shipment) holds the funds in escrow like any shipment payment; a standalone invoice is released to the shipper's balance at once. The office **sends** an invoice or a reminder with one click from the Collections board or the client's invoices tab (email, in-app for account holders, optional SMS), and **automatic reminders** go out a few days before the due date and on the configured days after it, each one logged on the invoice; settings per shipper (on/off, days, SMS, the email message). Customers with an account see all their invoices on the dashboard with outstanding and overdue totals. **Fill a barrel — consolidation** (`server/groupage.ts`; public page `/#/groupage`, shipper board `/#/dashboard/groupage`, customer tab *Shared barrels*): a shipper opens a shared slot on a sailing — one barrel that several people fill with bags and boxes, or a 20/40 ft container that several people fill with barrels — with capacity, price per unit, min/max per person, what's included, the closing date and the sailing date. Customers browse open slots by destination, watch the fill bar, and reserve the units they need (account required; nothing charged yet); the office is told on every reservation and when a slot fills. **Close & book** turns every reservation into a normal booked shipment — reference, tracking, pickup, labels, documents, and a payment of exactly the reserved amount through escrow — grouped under the slot; cancelling releases everyone with a note. The quote wizard points barrel/box senders to shared slots; the Gold Coast demo has a barrel 5/8 full and a 40 ft container 72/160 full. **Vehicle flow** (`server/vehicles.ts`; vehicle fields in the quote wizard, `VehicleCard` on every vehicle shipment): the quote captures VIN, year/make/model, RoRo vs container, title status (clean / lien / salvage / rebuilt) and whether it runs, so shippers price properly and see it on the lead; the VIN is decoded through NHTSA vPIC (`VPIC_URL` override) with a built-in year + make fallback. On the shipment the card holds the full vehicle record (body, engine, mileage, owner on the title, lien holder, declared value, goods packed inside), the **US export clearance** steps (documents received → filed with CBP under the 72-hour rule → cleared → loaded, with the AES ITN), a **handover** arrangement (where/when, notifies the other side) and the shipper's **handover checklist** (original title, ID, lien release, bill of sale/POA, keys, quarter tank, personal items, condition photos). The duty estimator is pre-filled from the vehicle's year, engine size, body and value. **Payments & escrow** (`server/payments.ts`; `PaymentCard` on every shipment for the customer and the office; shipper page `/#/dashboard/payments`; admin section at `/#/admin`): the customer pays **Ship Sync**, not the shipper. On a booked shipment the pay card totals what is due — the accepted quote (or the shipper's open invoice for that shipment) plus any insurance premium not yet collected — and *Pay securely* opens **Stripe Checkout** (card, Apple Pay, Google Pay). The money is **held in escrow** and released to the shipper's balance, less the platform take-rate (default 8%), when the shipment reaches the release milestone (in transit by default, or delivered — admin setting); a receipt lands in the documents vault, the insurance premium is marked collected, and an open invoice on the shipment is marked paid. The shipper's **Payments** page shows in-escrow / available / paid-out balances, the ledger with fees, a payout account (bank or mobile money, owner only — account numbers are masked for other staff) and **Request payout**; admins see every payment, settle payouts (mark sent with a transfer reference, or reject with a note that returns the funds to the shipper's balance), release held funds early, refund (Stripe refund; released funds can only be refunded by Ship Sync), and set the take-rate, release rule and customer/shipper notes. Money received outside the platform (bank, cash, mobile money) can be **recorded** by the office on the shipment — no fee, no escrow, but the same receipts and invoice bookkeeping. Stripe is called over plain HTTPS: set `STRIPE_SECRET_KEY` (test keys work without a live business account) and `STRIPE_WEBHOOK_SECRET` (point a Stripe webhook at `/api/payments/webhook` for `checkout.session.completed`, `checkout.session.expired` and `charge.refunded`; signatures are verified over the raw body and events are deduplicated). Without a webhook, payments are confirmed when the customer returns to the site (`POST /api/payments/:id/verify` asks Stripe for the session); without any key, online checkout is off and offline recording still works. `STRIPE_API_URL` points at a mock for tests; `APP_URL` builds the return URLs. Notification kind `payment` for both roles. Mobile-money collection (MTN MoMo, Paystack/Flutterwave) is designed to plug in behind the same escrow ledger. **Cargo insurance at checkout** (`server/insurance.ts`; `InsuranceCard` on every shipment for the customer and the office; admin section at `/#/admin`): the "insurance" checkbox is now a real product. The admin sets the product once — provider/underwriter name, coverage, premium % by cargo type (defaults 2%, 1.5% for vehicles and containers, 2.5% commercial), minimum premium, maximum insured value, deductible, Ship Sync's commission and the customer-facing terms — stored in a `settings` table so an insurer or MGA can be plugged in without code. On a booked shipment the customer (or the office on their behalf) declares a value, sees the premium live, accepts the terms and adds cover: a policy is issued with a certificate number, a **certificate of insurance** lands in the documents vault, and the office is told to collect the premium with the freight (and marks it collected). Cover can be cancelled before the goods leave the origin. Either side can **file a claim** (description, amount capped at the declared value, contact); the shipper and every admin are notified, and the admin settles or declines it from the Insurance panel, which also shows insured value, premiums written, commission and open claims. Notification kind `insurance` for both roles. **Duty & landed-cost estimator** (`server/duty.ts`; public page `/#/duty`, `DutyCard` on every GH/NG shipment for the customer and the office): answers "what will I pay at Tema?" from plain-English inputs — goods type, value, freight, and for vehicles the model year, engine size and body type. Ghana follows the GRA **ICUMS** assessment structure: ECOWAS CET duty band by goods type (vehicles 5/10/20% by engine size), VAT 15% + NHIL 2.5% + GETFund 2.5% on CIF + duty (flat since the 2026 VAT reform; the COVID-19 levy was repealed from 1 Jan 2026), ECOWAS 0.5%, AU 0.2%, EXIM 0.75% and Special Import 2% levies on CIF, the 1% examination fee and the over-age penalty on vehicles older than 10 years, with a returning-resident exemption toggle for personal effects. Nigeria is a coarser NCS model (duty + vehicle levy, 7% surcharge, CISS 1%, ETLS 0.5%, VAT 7.5%). Every result shows the line-by-line breakdown in cedis/naira and USD, the effective rate, the landed cost, the rate date, and — for Ghana — a link to the official GRA ICUMS general-goods or used-vehicle calculator to verify (those need an HS code, CPC and CIF in GHS, and value vehicles from GRA's own database, which is why they can't be called programmatically). Customers save their values on a shipment to keep the estimate; once customs assess, the office enters the **official assessment** (amount, ICUMS reference, note), which replaces the estimate for the customer, logs a tracking event and sends a notification. Rates and the indicative exchange rates (`GHS_PER_USD`, `NGN_PER_USD`) live in one place with the month they were checked. **Receiver experience** (`server/recipient.ts` + `server/sms.ts`; `RecipientPanel` on the Shipments board and the customer's dashboard; public page `/#/r/<token>`): the person actually waiting for the goods in Ghana or Nigeria gets a phone-first page — no sign-in — with the status, where and when to expect it, a *ready for collection* box with the reference and a QR code to show at the yard, the pieces, the history, and an **I received it** button (name + optional note, or *Something's wrong*) that marks the shipment delivered, ticks all pieces, and tells the sender and the office; problems are logged as an event and raise an alert instead. The consignee is **texted** (SMS, or WhatsApp when a Twilio WhatsApp sender is configured) with that link when the shipment sails, arrives, goes out for delivery and is delivered, and the office can send an intro, a *ready for collection* notice with pickup details, a reminder, or re-send any milestone from the panel — which also shows the message log, the link to copy, a WhatsApp share button and a tap-to-call. Phone numbers are normalised to E.164 from the consignee's country. Providers are pluggable: `SMS_PROVIDER=twilio|termii|africastalking|log` (auto-detected from `TWILIO_*`, `TERMII_*`, `AT_*` keys; `log` prints; none = texts skipped but the link still works); queued texts retry every five minutes. A company-wide switch lives under Notifications → *Receiver texts* (owners/dispatchers). **Pickup scheduling** (`server/pickups.ts`; `PickupCard` on the customer dashboard and the Shipments board; office page `/#/dashboard/pickups`): the shipper publishes weekly **pickup hours** — weekday, time window, optional area, max pickups per window — and how many days' notice they need. A customer with a booked shipment picks a day and window from the slots that fit (lead time and capacity respected), enters the collection address, contact and notes, and the request lands on the office's Pickups page; **Confirm** adds the address — geocoded — as a stop on that day's pickup run (created if needed, or pick an existing one), the driver sees it in My runs, and marking the stop done moves the shipment to Picked up and the booking to Collected. Either side can move or cancel a pickup (customer changes go back to *awaiting confirmation*; office changes stay confirmed and re-place the stop), and the other side is notified every time (notification kind `pickup`). The office can also book on a customer's behalf, which confirms straight away. Gold Coast is seeded with Mon/Wed/Fri morning and afternoon windows from Houston plus Saturday mornings anywhere. **Documents vault** (`server/documents.ts`; `DocumentsPanel` on the Shipments board and the customer's dashboard; viewer at `/#/dashboard/documents/:id`, public share links at `/#/doc/<token>`): every shipment has a folder. The office **generates** a packing list, commercial invoice or proof of delivery from what the platform already knows (sender, consignee, pieces and their labels, container/vessel, accepted quote or invoice, the delivery scan with receiver and photo) — regenerating refreshes the same document — and **uploads** anything else (bill of lading / AWB, customs forms, ID scans, insurance certificates, photos; PDF or image up to 6 MB, stored in Postgres as base64). Each document is *office only* or *customer can see*; customers see shared documents on their dashboard, can upload their own (ID, supplier invoice) and delete only those, and get a notification when a document is added for them, as the office does for customer uploads. Share links open the document without signing in and can be revoked. Generated documents render as printable white sheets (print / save as PDF); uploads preview inline (images, PDFs) or download. Shipment lists carry a document count. **Rate cards** (`/#/dashboard/rates`, `src/pages/Rates.tsx`, API in `server/rates.ts`): shippers publish prices per lane — origin (or any origin they serve), destination, mode and cargo type — as a price per piece or per kg with a minimum charge and optional pickup, door-delivery and insurance fees, transit days, how long the quote stays valid and the notes that go on it. A card set to **send instantly** turns a matching request into a quote the moment it is posted (the customer is told it's an instant quote, the office that it went out), beating any manual reply; the rest surface as a **suggested price** on the lead with a full breakdown and one-click prefill of the quote form. The public quote flow shows a published-rate estimate next to each matching shipper (and flags which will quote instantly), a *Try a quote* calculator on the rates page prices any scenario against the shipper's cards, and owners/dispatchers can pause, duplicate for another origin or delete cards (agents can view). Exact-origin cards beat any-origin cards; for an "either" mode request the cheaper mode wins. Shippers with published cards are left out of the demo auto-quote simulator. Gold Coast is seeded with six Ghana lanes (two instant). **Notifications** (`server/notify.ts`, bell in the header + `/#/dashboard/notifications`, `src/pages/Notifications.tsx`): every event writes an in-app notification and, when the user wants it and email is configured, an email. Customers hear about new quotes (including the demo auto-quotes), the booking confirmation when they accept one, and the milestones that matter — picked up, on its way (with the vessel), arrived, out for delivery, delivered (who received it, and whether a proof-of-delivery photo is on the tracking page — the public tracking page now shows the POD card with the photo once the last piece is scanned). Shipper teams (owner, dispatcher, agent — drivers are left out) hear about new leads on their lanes, accepted quotes, deliveries, container updates from the line (number assigned, vessel, ETA change, milestones) and invoices that have gone overdue (one alert per invoice, swept every six hours). All status-change paths — manual advance, container cascade, driver run stops and sticker scans — go through `notifyShipmentStatus`, which dedupes per shipment and status. Preferences per user: email on/off and a mute list per kind; a *Send a test email* button checks the setup. Email goes through [Resend](https://resend.com) when `RESEND_API_KEY` and `EMAIL_FROM` are set (`APP_URL` makes the buttons link back to the app; `EMAIL_PROVIDER=log` prints to the console instead), queued rows are retried every five minutes up to five attempts, and without a provider the bell still works and emails are marked skipped. The bell polls every 45 s while the tab is visible. Shippers also run their operation from the workspace, on three boards that share the same shell (`src/components/board.tsx`: stat cards that filter, chips, search, sortable paginated tables with expandable rows, an actions menu, and a confirm dialog for anything destructive): **Team** (`/#/dashboard/team`) invites staff with one-time join links (`/#/join?token=…`) and roles enforced server-side — owner, dispatcher, agent, driver — with role changes inline, invite links revealed per row, and deactivate/reactivate behind a confirm; **Fleet** tracks vans and trucks on both sides with type/base filters, total rated capacity, inline editing and maintenance/retire/reinstate from the menu; **Routes** groups booked shipments into pickup runs and arrived shipments into delivery runs, geocodes addresses through OpenStreetMap Nominatim (cached, 1 req/s; `NOMINATIM_URL` overrides it for tests), orders stops nearest-neighbour + 2-opt, lets you drag pins to fix positions, with Start / Mark done / Cancel from the board (finishing early or cancelling asks first), and hands the run to a driver whose simplified **My runs** view marks stops done — which moves the shipment to Picked up / Delivered on the customer's tracking page (`server/ops.ts`). **Going live checklist.** Accounts: `POST /api/auth/forgot` emails a one-hour reset link (`/#/reset?token=…`, `password_resets` table; always answers OK so emails can't be enumerated) and `POST /api/auth/reset` sets the new password, signs the user in and signs them out everywhere else; the "Forgot password?" link sits under the sign-in password field. Sign-in is throttled (30 attempts per IP and 10 per email every 15 minutes, cleared on success), sign-up 10 per IP per hour, forgot 3 per email per hour. Set `HIDE_DEMO_SHIPPERS=true` to keep the fictional seed shippers out of the public directory, matching and home-page stats (they stay in the database and in admin; the demo sign-in hint disappears) and `DEMO_AUTO_QUOTES=false` to stop them auto-replying; the platform's own `ship-sync-sourcing` entry is never listed publicly. **Admin → System** (`src/components/AdminSystem.tsx`, `server/system.ts`) shows what is wired (database type, email, SMS, Stripe, AIS, Terminal49, contact details, demo flags — never the secret values), an **error log** (`app_errors`: every server 500 with route, stack and user, browser crashes posted by `src/lib/errors.ts` to `POST /api/site/client-error`, and failed background jobs; resolve one or all), **database backups** (a JSON export of every table runs nightly at `EXPORT_HOUR_UTC`, default 03:00, into `EXPORT_DIR`, default `./data/exports`, keeping the last `EXPORT_KEEP`, default 14; "Export now" and per-file download from the admin page; `EXPORT_NIGHTLY=false` disables) and the contact-form inbox. The client is code-split: the marketing core (home, quote, directory, track, auth, company pages) is one ~430 kB entry chunk; every dashboard page, the sourcing desk, admin and the MapLibre map load on demand, so a first visit downloads about a sixth of what it used to.

**Admin is now tabbed** (`/#/admin?view=…`, `src/pages/Admin.tsx`): **Business** (`GET /api/admin/business`, `server/business.ts`) is the founder's view — revenue by stream (take-rate on escrow, sourcing service fees, sourcing goods billed, subscription MRR from plan counts × the published prices), GMV, refunds, the money held (escrow now, released-not-paid-out, payouts requested, on hold), 12-week growth series with sparklines (customer and shipper signups, requests, bookings, sourcing, GMV), the request → quote → booking funnel with hours-to-first-quote, demand by destination and by lane with unquoted counts (where to recruit shippers), sourcing pipeline by stage and agent commissions, shipper/customer health and review averages; with `HIDE_DEMO_SHIPPERS=true` demo rows drop out of every figure. **Attention** (`GET /api/admin/exceptions`) is the platform-wide needs-a-person board: requests unquoted after 48 h, shipments 2+ days past ETA or 10 days without an event, escrow held 45+ days / on hold / still held after delivery, disputes idle 3+ days, payouts waiting 3+ days, unverified real shippers after 3 days, sourcing jobs unassigned 24 h / quotes unanswered 7 d / no movement 14 d, unanswered contact messages and unresolved errors — grouped by kind, most urgent first, each card linking where it is fixed.
